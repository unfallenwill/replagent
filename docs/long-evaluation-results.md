# 第二轮组合与长程评估

2026-10-26—27，使用本机配置的 `MiniMax-M3.1-Flash`、`effort=max`、并发三。
生产 agent、REPL 和 1021 字符 system prompt 保持不变。
任务、预算与参考解校验方法见 [长程评估说明](long-evaluations.md)。

## 基线结果

原有 20 项基础任务每项三次：60/60 通过，与原基线比较无回归。
新集 8 项每项三次：23/24 通过；开发集 15/15，留出集 8/9。
8 个任务都有至少一次成功，其中 7 个任务三次全过。

| 任务                 | 通过试验 | 平均模型调用 | 平均耗时 |
| -------------------- | -------: | -----------: | -------: |
| 跨模块优惠券         |      3/3 |         13.3 |  2分20秒 |
| CSV处理管线          |      3/3 |         15.7 |  8分45秒 |
| 异步缓存迁移         |      3/3 |         18.3 |  4分10秒 |
| 96分片增量处理       |      3/3 |         16.3 |  3分33秒 |
| 7轮连续需求          |      3/3 |         33.3 |  3分54秒 |
| 依赖调度器（留出）   |      2/3 |         10.3 |  3分30秒 |
| 40层配置继承（留出） |      3/3 |         21.0 |  3分38秒 |
| 7轮迁移恢复（留出）  |      3/3 |         28.0 |  5分22秒 |

平均耗时和调用次数包含失败试验。调度器失败那次仅耗时约 4.5 秒、调用一次，
因此其平均耗时不能单独用来判断效率。

唯一失败是正常结束但未完成任务：模型先列出目录，将目录列表通过 `say` 发出，
工作区没有修改，三个功能检查均失败。框架没有把一次正常结束或现有简单测试通过当作任务成功。
该结果保留在正式基线，没有用重跑替换。当前已有的“完成后再 say”和“中间观察用 deposit”
说明没有完全避免这次通道误用；仅凭当前数据不能断言增加一句 prompt 就能稳定解决。

迁移恢复三次均通过，覆盖逐轮只读约束、先验证再迁移、旧备份保持原始字节、
幂等重跑、外部输入更新、单文件回滚和再次迁移。
这里的恢复是业务文件操作恢复，不代表 agent 跨进程会话恢复。

## 运行长度与消耗

新集共 469 次模型请求，平均每次试验 19.5 次；最多 49 次。
平均每次约 4分24秒，最长约 11分32秒。单次请求最高输入 48667 token。
总输入 7934107 token、总输出 620174 token；输入包含端点上报的缓存流量。
缓存计量并非每次都完整，不能据此推算实际费用。

7轮连续需求的三次基线分别使用 21、30、49 次调用，虽然都通过，消耗仍有较大波动。
原基础集本轮平均每次 3.13 次调用、约 21 秒；两组任务和预算不同，这不是候选版本之间的效率对照。
本轮新增任务已经产生更长的执行与上下文，但仍是合成工程任务，不能替代小时级真实仓库验证。

## 请求文本构成

按实际请求中的字符数累计，system 占约 1.5%，用户消息与观察约 22.9%，
历史 assistant 代码约 28.5%，回放的模型思考文本约 47.1%。
这是重复请求的文本字符构成，不是 tokenizer 结果或费用分解；不包含不透明签名等元数据。

当前 system 已很短。下一轮可以分别检验观察摘要、程序复用与可由模型主动触发的上下文整理，
重点看是否降低每次成功的消耗，同时保留先前需求和 REPL 状态。
本轮没有据留出集失败修改 prompt/harness，也没有完成候选之间的消融对照。

## 关键任务复验

同一候选、任务和预算，另外运行 10 次 `long/development/evolving-policy`。
10/10 通过，共 70 次用户请求，所有逐轮验收通过。
模型、端点、effort、并发、预算、候选、prompt、生产源码、任务和评分实现指纹均已核对一致。
它是独立复验，重复次数不同，不与三次基线直接进行回归门禁比较。

共 280 次模型请求，平均每次试验 28 次，范围 11—47 次；
耗时范围约 1分02秒—5分36秒，平均约 3分40秒。
输入 4063376 token、输出 261845 token，其中输入缓存流量 3741754 token；
单次请求最高输入 50913 token。
每次成功的输入加输出总量介于 40168—715881 token，约有 17.8 倍差异。
这些数包含缓存流量，表示上报的 token 消耗，不表示费用存在同样倍数的差异。

已通过的试验中，一个 11 次调用的实现首轮用了 5 次，随后六轮每轮仅 1 次；
另一个 49 次调用的实现每轮用了 6—10 次。评分允许不同工具路线和调用数量，
因此可以同时识别满足要求的高效实现和真实的提前结束，不能单凭步数判定好坏。
